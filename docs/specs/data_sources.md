| 最優先方針 | **データ鮮度の保証**（古い値を黙って残さない） |

---

## 1. 背景：なぜ再選定したか

旧構成 `yfinance + EDINET DB + IRBANK(スクレイピング)` のうち、**IRBANKのHTMLスクレイピングが鮮度劣化の主因**だった。
HTML構造に依存するため取得失敗時に黙って古い値が残り、`irbankDate: 2025-05-15`（1年以上前 = freshness `critical`）の銘柄が発生していた。
yfinanceも非公式ゆえROE/配当などの項目が時々NaN化し、「黙って劣化」するリスクを抱えていた。

→ **壊れにくい公式APIに寄せ、鮮度を"保証"できる構成へ再設計する。**

---

## 2. 確定構成（A案：月¥1,650）

| 層 | 用途 | 採用ソース | 鮮度 | 料金 |
|---|---|---|---|---|
| L1 | スクリーニング（株価・PER・PBR・ROE・配当・出来高・時価総額・52週高安） | **J-Quants Light**（主） + yfinance（即時参考の補助） | T+1（翌営業日） | ¥1,650/月 |
| L2 | 決算詳細分析（四半期業績・進捗率・自己資本比率・特別損益・業績修正・MD&A） | **EDINET DB**（主） + EDINET公式API（一次情報backstop） | 毎日8:00 JST更新／開示当日 | 無料 |
| L3 | マクロ（エコノミストレポート） | web_fetch（Claude側） | 直近1週間〜1ヶ月 | 無料 |

**IRBANKスクレイピングは廃止。**

---

## 3. 各ソースの選定理由

### J-Quants Light（L1主軸）
- **日本取引所グループ（JPX）公式**。データの正確性・鮮度が制度的に保証される。
- 無料版は**12週間遅れ**で半年運用には致命的 → Light（¥1,650/月）で**T+1（翌営業日）**鮮度を確保。
- 株価四本値・財務情報ともに**5年分**、1契約で取得可能。
- レート制限に注意（無料版で5回/分。Lightは緩和されるが詳細は要確認）。

### yfinance（L1補助）
- 無料・当日終値〜15分遅延で即時の参考値として有用。
- ただし非公式で項目欠落リスクがあるため、**鮮度保証の主軸にはしない**（J-Quantsを正とする）。

### EDINET DB（L2主軸・継続）
- 金融庁EDINETのXBRLを整形した無料API（**100回/日**）。
- **毎日8:00 JST自動更新**、**決算短信(速報)対応**、142指標を整形済。AI分析（Claude）にも対応。
- 株価は持たないため、PER/PBR算出は L1（J-Quants/yfinance）と組み合わせる。

### EDINET公式API（金融庁・L2 backstop）
- **一次情報**。開示当日に取得可能。生XBRLのためパース負荷は高いが、EDINET DBの値の検証・補完に使う。

### 不採用
- **J-Quants Free**：12週間遅れで鮮度NG。
- **立花証券e支店API**：リアルタイム無料だが口座開設＋電話認証＋構築の手間（B案候補）。
- **バフェットコードAPI**：Web APIはプレミアムのみで高額、個人にはオーバースペック。
- **TDnet公式API**：基本料7万円で個人非現実的。

### 1aの設計ポイント（鮮度保証の核心）
- 旧構成はEDINET取得失敗時に**IRBANKへ黙ってフォールバック**していた。これがHTML構造依存で失敗し、古い値が残る原因だった。
- 新構成は**フォールバックしない**。取得できなければ `unavailable` として記録し、UI（鮮度バナー）に「財務未取得N件」と赤字表示する。
- → 「黙って劣化する」経路を物理的に排除した。
- **2026-09-04 追記**: この設計は `fetch_stocks.py` までは実装されていたが、`update_data.py` が
  `unavailable` を `irbank` に丸めていたため画面まで到達していなかった（BUG-006）。修正済み。

### 1bの鮮度バナー仕様
- `pipelineMeta.runDate` とブラウザ実日付から経過日数を算出。
- `≤7日`=✅最新（緑）／`≤30日`=⚠️やや古い（黄）／`>30日`=🔴要更新（赤・refresh推奨バッジ）。
- `screeningStocks` の `freshness` を集計し `stale`/`critical` 件数、`dataSource==='unavailable'` 件数を併記。

## 5.5 株価の鮮度維持（2026-09-04 追加）

株価と財務は変化する頻度が違うため、更新経路を分けた。

| | 更新手段 | 所要 | EDINET消費 | 鮮度の目標 |
|---|---|---|---|---|
| 株価・PER・PBR・配当・52週高安 | `refresh_prices.py`（画面のボタンからも実行可） | 約12秒 | 0回 | **2営業日以内** |
| 財務・罠検出・6項目評価 | `fetch_stocks.py` → `update_data.py` | 約13分 | 最大80回 | 30日以内 |

- `pipelineMeta.priceDate` が株価、`pipelineMeta.runDate` が財務の取得日を表す。
- `priceDate` は**実行日ではなく実際に値が付いた日**（yfinance の `regularMarketTime` を
  取引所ローカル日付に変換したもの）。夜間や休日に更新しても前営業日の終値に当日の日付を貼らない（BUG-012）。
- 株価の鮮度は**営業日ベース**で判定する（金曜終値を月曜に見ても「1営業日前」となり誤警告しない）。
- `refresh_prices.py` は財務項目を書き換えない。取り直していないものを新しく見せないため。
- 銘柄の入れ替えには株価更新では不十分で、フルスクリーニングが必要（母集団の再評価を伴うため）。

### 鮮度判定の一元化（2026-09-13）
鮮度の計算としきい値は `src/freshness.ts` だけに置く。画面ごとに持つと基準日がずれる（BUG-013）。

| 対象 | 基準 | しきい値 | 定数 |
|---|---|---|---|
| 株価 | `pipelineMeta.priceDate` からの**営業日** | 2以内=✅ / 4以内=⚠️ / 超=🔴 | `PRICE_BIZ_DAYS` |
| 財務（全体） | `pipelineMeta.runDate` からのカレンダー日 | 7以内=✅ / 30以内=⚠️ / 超=🔴 | `pipelineMeta.staleWarnDays` |
| 財務（銘柄別） | `irbankDate`（決算開示日）からのカレンダー日 | 30=fresh / 60=normal / 90=stale / 超=critical | `FRESHNESS_DAYS` |
| マクロ | `macroMeta.generatedDate` からのカレンダー日 | 7以内=✅ / 14以内=⚠️ / 超=🔴 | `MACRO_DAYS` |

**判定の色と、画面に出す文言は別物として扱う（2026-09-26 追加・BUG-022）。**
株価の色（✅/⚠️/🔴）は上表の営業日数で正しく決まるが、
**経過営業日数 0 は「今日」を意味しない**。土曜・日曜に金曜終値を見ると営業日数は 0 だが、
日付は前営業日のものである。`0 → '本日'` と表示していたため、
週末は必ず「本日」の横に前日の日付が並ぶ状態だった。
文言の組み立ては `freshness.ts` の `priceFreshnessLabel()` に集約する。

| 状況 | 表示 |
|---|---|
| カレンダー日数 0（当日取得） | 本日 |
| 営業日数 0 だがカレンダー日数 1 以上（土日） | 前営業日 |
| それ以外 | N営業日前 |
| 基準日が未来 | 基準日が未来（要確認） |
| 基準日が無い・壊れている | 取得日不明 |

**実行時に計算した鮮度タグは保存しない。** `Stock.freshness` は 2026-09-13 に削除した。
保存すると、データは変わっていないのに時間の経過で判定だけが実際とずれる。
`macroMeta.generatedDate` が無い場合は記事日付で代用せず「実行日不明」と出す
（1か月前の分析でも参照記事が新しければ緑になってしまうため）。

## 5.55 銘柄マスター（JPX）の扱い（2026-09-15 追加）

母集団は JPX の銘柄一覧 Excel から作る。

| 項目 | 内容 |
|---|---|
| 配布URL | `https://www.jpx.co.jp/markets/statistics-equities/misc/tvdivq0000001vg2-att/data_j.xlsx` |
| 配布ページ | https://www.jpx.co.jp/markets/statistics-equities/misc/01.html |
| 定数 | `fetch_stocks.JPX_MASTER_URLS`（旧 `.xls` を予備として保持） |

**2026年に `.xls` → `.xlsx` へ変更され、旧URLは404になった（BUG-015）。**
ステータスコード・Content-Type・列数を検証し、失敗時は配布ページのURLを添えて停止する。
黙って壊れたデータで進むと、無関係な例外（`Excel file format cannot be determined`）になって原因が分かりにくい。

### 除外するもの
| 対象 | 方法 | 理由 |
|---|---|---|
| ETF・ETN | 市場区分（プライム／スタンダード（内国株式）のみ残す） | 個別株ではない |
| 業種コードなし | `sector33_code` が数字でないものを除外 | 33業種に分類されない |
| **種類株式・優先株** | **銘柄コードが4文字（`[0-9A-Z]{4}`）のものだけ残す** | 親会社と同じ市場区分・同じ業種で登録されており、他のフィルタを通過する（BUG-017） |

銘柄コードは通常4文字で、数字のほか `253A` のような英数字もある。
種類株式だけが5文字（例: `50765` インフロニア・ホールディングス第１回社債型種類株式）。
除外した銘柄はコードと名称を実行ログに出す。

## 5.6 罠検出10ルールと「判定不能」（2026-09-10 追加）

EDINET DB は有報80項目＋決算短信31項目を返すが、当初は13項目しか使っていなかった。
未使用だった項目のうち、実測で取得率100%だったものを罠検出に追加し、5→10ルールに拡張した。

各ルールは **該当 / 非該当 / 判定不能** の3状態を返す。
判定不能を非該当と同じ扱いにすると「測っていないだけ」の項目が「問題なし」に見えるため、
`detect_trap_v2()` は `undetermined`（「ルール名: なぜ測れないか」）を分けて返す。

| # | ルール | 使用項目 | 該当条件 | 判定不能になる条件 |
|---|---|---|---|---|
| 1 | ROE急騰 | `roe_official` | 直近 > 過去平均×2.0 | 過去4期ぶんのROEが無い |
| 2 | EPS急騰 | `eps` | 直近 > 過去平均×2.5 | 過去4期ぶんのEPSが無い |
| 3 | 特別利益の上乗せ | `net_income`, `ordinary_income` | 純利益 > 経常利益×0.9 | 会計基準がIFRS/US GAAP（経常利益の概念が無い）／経常利益が赤字 |
| 4 | 赤字急回復 | `ordinary_income` | 過去に赤字期あり & 直近黒字 | 過去3期ぶんが無い |
| 5 | 自己資本比率 | `equity_ratio_official` | 40%未満 | 取得できていない |
| 6 | 営業CFと純利益の乖離 | `cf_operating`, `net_income` | 営業CF < 純利益×0.5 | 営業CFが無い／純利益が黒字でない |
| 7 | 売上債権の急増 | `trade_receivables`, `revenue` | 売上債権の伸び − 売上の伸び > 20pt | 2期ぶんのデータが無い |
| 8 | 在庫の急増 | `inventories`, `revenue` | 在庫の伸び − 売上の伸び > 20pt | 2期ぶんのデータが無い |
| 9 | 有利子負債の水準 | `short_term_loans`, `long_term_loans`, `current_portion_lt_loans`, `net_assets` | 有利子負債 > 純資産（D/E > 1.0倍） | 借入金がタグ付けされていない／一部欠損で合計を確定できない |
| 10 | のれんの規模 | `goodwill`, `net_assets` | のれん > 純資産の30% | のれんがタグ付けされていない |

判定は該当1件で `suspicious`（−15点）、2件以上で `dangerous`（−30点）。

### ルール9の扱い（部分取得の場合）
3項目のうち一部しか取得できないことがある。取得できたぶんの合計は実際の有利子負債の**下限**なので、
- 下限が閾値を超えた → 実際も超えているので**該当と断定できる**
- 下限が閾値以下だが欠損項目がある → 超えていない保証が無いので**判定不能**

とする。欠損を0円とみなすと、借入の多い企業を「健全」と表示してしまう。

### ルール10の扱い
のれんが `null` のとき「M&Aをしていない」のか「XBRLにタグ付けされていない」のかを
EDINETのデータからは区別できないため、0億円とみなさず判定不能とする。

### 実測データ充足率（2026-09-10・上位15社）
| 項目 | 取得できた社数 |
|---|---|
| `cf_operating` / `trade_receivables` / `inventories` / `revenue` / `net_income` / `total_assets` | 15/15 |
| `short_term_loans` | 11/15 |
| `impairment_loss` | 8/15 |
| `long_term_loans` / `current_portion_lt_loans` | 6/15 |
| `goodwill` | 5/15 |

中小型株はXBRLタグ付けが疎で、ルール9・10は判定不能になりやすい（`dashboard.md` L-12）。

## 5.7 一次資料へのリンク（2026-09-10 追加）

数値だけを表示して出所に辿り着けない状態を避けるため、EDINETから以下のURLを持ち回る。

| フィールド | 取得元 | 取得率（15社） | 表示場所 |
|---|---|---|---|
| `EdinetDetail.edinetUrl` | `financials[].edinet_view_url`（無ければ `edinet_filing_url`） | 15/15 | 深掘り画面「一次資料で確認する」／ポートフォリオ画面の財務一覧 |
| `EdinetDetail.earningsPdfUrl` | `earnings[0].pdf_url` | 12/15 | 同上 |
| `EdinetDetail.earningsTitle` | `earnings[0].title` | 14/15 | リンクの補足表示 |

決算短信PDFのURLは発行体サイトを指すため、EDINETと違い恒久的とは限らない。
タイトルにはスクレイプ元のHTML由来の文字列（`keyboard_arrow_right`・`【PDF：260 KB】`・末尾のファイルサイズ）が
混ざることがあるため `clean_title()` で除去してから保存する。

## 6. 既知の課題・制限事項
- J-Quants Lightのレート制限の実値は契約後に実測して `refresh.py` のスリープを調整する。
- EDINET DBは株価を持たないため、L1とL2のコード対応付け（証券コード⇄EDINETコード）を維持する必要がある（`scripts/cache/edinet/code_map.json`）。
- yfinance は非公式のため項目欠落・異常値のリスクが残る（実際に配当利回りの異常値補正が発生している）。
  2営業日以内の鮮度を「保証」するには J-Quants Light（T+1保証）への移行が必要で、
  現状の `refresh_prices.py` は「たいてい2営業日以内に保てる」水準にとどまる。
- yfinanceとJ-Quantsで指標定義が微妙に異なる場合があるため、ダッシュボード表示は**J-Quantsを正**とし、差異が出たら検証ログに記録する。
